WHY: Reports end up in CI logs and chat; printing the secret would spread the leak further.

=== S3.2/2
Q: The key was removed in the latest commit. Why must it still be rotated?
+ It remains in the git history, where anyone with the repository can find it.
- Removing it isn't possible.
- Rotation is required every month anyway.
- The key was never really removed.
WHY: History scans find secrets in old commits. Once pushed, assume a secret is compromised.

=== S3.2/3 pick
Q: An allowlist entry for a dev password expired last month. How is that finding reported?
+ `c0c6e22f18bb8635  config/dev.toml              REPORTED: allowlist entry expired 2026-10-01`
- `fffbea3d6a6ebb12  tests/fixtures/fake_aws.py   accepted (AWS documentation example key, until 2027-06-01)`
- `09fc24b536f74f38  scripts/deploy.sh            REPORTED: new finding`
WHY: Expiry dates stop "temporary" exceptions from becoming permanent; someone must look again.

=== S3.3/2
Q: Why are dependency names normalised before comparing?
+ So `Requests`/`requests` and `python_dateutil`/`python-dateutil` match as the same package.
- To shorten long names.
- PyPI requires lower-case names in files.
- To hide package names from attackers.
WHY: Package names are case-insensitive and treat `-`, `_` and `.` alike, so normalising avoids missed matches.

=== S3.3/3
Q: What happens when the vulnerability API is unreachable?
+ A warning is reported for that package instead of crashing, and earlier answers come from the cache.
- The scan reports no vulnerabilities.
- The program exits with an error immediately.
- It retries forever.
WHY: A security tool should fail visibly, not silently: "could not check" is very different from "no known vulnerabilities".

=== S3.4/2
Q: Exit codes use bit flags: 1 for secrets, 2 for dependencies. What does exit code 3 mean?
+ Both secrets and vulnerable dependencies were found.
- Three problems were found.
- An internal error.
- Only dependencies were found.
WHY: Each kind of problem sets its own bit, so a pipeline can test the bits to block on secrets but only warn on dependencies.

=== S3.4/3
Q: Why run the auditor as a pre-commit hook as well as in CI?
+ The hook stops secrets before they reach history; CI catches whatever slips through.
- CI can't scan secrets.
- Hooks replace CI.
- Hooks make commits faster.
WHY: Catching a secret before it's committed avoids rotation entirely. CI is the safety net.
