=== A14.1
@idea
**Big-O notation** describes how the work a piece of code does grows as its input grows, ignoring constant factors. A loop over the input once is O(n): double the data, double the time. A loop inside a loop over the same data is O(n²): double the data, four times the time. Halving the problem at every step, as binary search does, is O(log n): a million items need about 20 steps and a billion about 30. Interviewers ask about it because it predicts which code survives real data volumes, long before you profile anything.

The everyday Python operations have known costs worth memorising: indexing a list, appending to it and looking a key up in a `dict` or `set` are O(1) on average; `x in some_list`, `list.index`, `list.insert(0, x)` and `min`/`max` are O(n); `sorted()` is O(n log n). A surprising number of slow programs are a hidden O(n) inside a loop, such as `if item in seen_list:` where `seen` should have been a set.

**Sorting algorithms** come up in interviews and roadmaps because they teach divide and conquer. **Merge sort** splits the list in half, sorts each half, then merges two sorted lists in one pass: log n levels of n work each, so O(n log n), and it is **stable** (equal items keep their order). Python's own `sorted()` uses Timsort, a merge-sort hybrid that is also stable and very fast on data that is partly sorted already. **Binary search** finds a value in sorted data by comparing with the middle and discarding half; the standard library's `bisect` module does it in C. In real code you call `sorted()` and `bisect`; writing them yourself once is how you understand their cost and their edge cases.
@how
- Count the loops over the input: one is O(n), nested is O(n²), halving is O(log n), sorting is O(n log n).
- Replace `x in list` inside a loop with a set or dict built once: O(n²) becomes O(n).
- Sort once, then search many times with `bisect.bisect_left` (O(log n) per search).
- Use `sorted(items, key=...)`; it is stable, so sort by the secondary key first, then the primary.
- `bisect_left` returns the insertion point; check `i < len(a) and a[i] == x` to know whether x is there.
@example python: An accidental O(n²) and its O(n) fix
import time

emails = [f"user{i}@example.com" for i in range(20_000)]
emails += emails[:5_000]          # 5,000 duplicates at the end

start = time.perf_counter()
seen_list, dupes_slow = [], 0
for e in emails:
    if e in seen_list:            # scans the whole list every time: O(n) inside a loop
        dupes_slow += 1
    else:
        seen_list.append(e)
slow = time.perf_counter() - start

start = time.perf_counter()
seen_set, dupes_fast = set(), 0
for e in emails:
    if e in seen_set:             # hash lookup: O(1) on average
        dupes_fast += 1
    else:
        seen_set.add(e)
fast = time.perf_counter() - start

print("duplicates:", dupes_slow, dupes_fast)
print(f"list version is about {slow / fast:,.0f} times slower" if slow > fast * 20 else "the set version is much faster")
@note
Both loops look the same, but `in` on a list is a linear scan, so the first version does roughly n²/2 comparisons. Changing one data structure turns it into O(n). This is the most common real-world Big-O bug, and spotting it is a favourite interview question.
@example python: Stable sorting by two keys, and bisect for lookups
import bisect

shifts = [("Ada", "Mon", 6), ("Grace", "Tue", 8), ("Linus", "Mon", 8), ("Ada", "Tue", 4), ("Grace", "Mon", 6)]
by_name = sorted(shifts, key=lambda s: s[0])          # secondary key first
by_day_then_name = sorted(by_name, key=lambda s: s[1]) # primary key second: ties keep name order
for s in by_day_then_name:
    print(s)

cut_offs = [0, 500, 1_000, 5_000]      # sorted thresholds in cents
labels = ["small", "medium", "large", "huge"]
for amount in (250, 500, 4_999, 12_000):
    print(amount, labels[bisect.bisect_right(cut_offs, amount) - 1])
@note
Because the sort is stable, sorting by name and then by day gives day order with names alphabetical inside each day. `bisect_right` finds which band a value falls into with a binary search instead of a chain of `if` statements, which stays fast however many bands there are.
@mistakes
- **`x in list` inside a loop.** Each check is O(n), so the loop becomes O(n²). Build a set once.
- **Binary search on unsorted data.** It silently gives wrong answers; sort first, or keep the data sorted with `bisect.insort`.
- **Re-sorting inside a loop.** Sorting is O(n log n); sort once outside the loop, or use a heap if you need the smallest item repeatedly.
- **Off-by-one in hand-written binary search.** Use a half-open range `[lo, hi)` with `while lo < hi`, or just use `bisect`.
@keys
- Big-O predicts how work grows with input: O(1), O(log n), O(n), O(n log n), O(n²).
- Sets and dicts give O(1) membership; lists give O(n).
- Merge sort and Timsort are O(n log n) and stable.
- Binary search is O(log n) but needs sorted data; `bisect` does it for you.

=== A14.2
@idea
A **tree** stores items in nodes that point to children. In a **binary search tree** (BST), every node's left subtree holds smaller values and its right subtree larger ones, so a lookup compares with the root and goes left or right, discarding a whole subtree each time. When the tree is **balanced**, its height is about log2(n) and every operation is O(log n). The catch is the shape: inserting already-sorted data sends every value to the right and the "tree" becomes a linked list of height n. Production code uses self-balancing trees (red-black or AVL trees, as in Java's TreeMap or C++'s std::map) that rotate nodes to keep the height logarithmic.

Walking a BST **in order** (left subtree, node, right subtree) visits the values in sorted order, which is why trees appear wherever ordered data and range queries are needed: database indexes (B-trees, a wide cousin of the BST), file systems and sorted containers. In Python you rarely build one: `dict` and `set` are hash tables (faster for exact lookups, but unordered by value), `bisect` on a sorted list covers many range queries, and the `sortedcontainers` package provides fast sorted collections.

A **heap** is a different tree with a weaker rule: every parent is smaller than its children. That is not enough to search, but it is exactly enough to always know the smallest item, so it is the standard **priority queue**. Python's `heapq` stores the heap in a plain list (the children of index i live at 2i+1 and 2i+2), with O(log n) push and pop and O(1) peek at `heap[0]`. Use it for schedulers, "the k most expensive queries", merging sorted files, and shortest-path algorithms such as Dijkstra's.
@how
- BST lookup and insert: compare, go left or right, stop at None; cost is O(height).
- In-order traversal (left, node, right) yields sorted values.
- Balanced height is about log2(n); sorted inserts give height n.
- `heapq.heappush(h, item)`, `heapq.heappop(h)`, `h[0]` to peek; use `(priority, counter, item)` tuples to break ties.
- `heapq.nlargest(k, data)` and `nsmallest` for top-k; `heapq.merge(*sorted_iterables)` for merging.
@example python: Why the tree's shape decides its speed
class Node:
    def __init__(self, value):
        self.value, self.left, self.right = value, None, None

def insert(root, value):
    if root is None:
        return Node(value)
    node = root
    while True:
        side = "left" if value < node.value else "right"
        child = getattr(node, side)
        if child is None:
            setattr(node, side, Node(value))
            return root
        node = child

def height(node):
    return 0 if node is None else 1 + max(height(node.left), height(node.right))

import random
values = list(range(1, 501))
shuffled = values[:]
random.Random(1).shuffle(shuffled)

balanced_ish, chain = None, None
for v in shuffled:
    balanced_ish = insert(balanced_ish, v)
for v in values:
    chain = insert(chain, v)
print("random order: height", height(balanced_ish))
print("sorted order: height", height(chain))
@note
The same 500 values give a tree about 20 levels deep when inserted in random order, but a chain 500 deep when inserted in sorted order, so every lookup in the second tree is a linear scan. Self-balancing trees exist to make the first case guaranteed instead of lucky.
@example python: A task scheduler with heapq and a tie-breaking counter
import heapq, itertools

counter = itertools.count()
queue = []

def add(priority, task):
    heapq.heappush(queue, (priority, next(counter), task))

add(2, {"name": "send report"})
add(1, {"name": "restart worker"})
add(2, {"name": "rotate logs"})
add(0, {"name": "page on-call"})

while queue:
    priority, _, task = heapq.heappop(queue)
    print(priority, task["name"])
@note
Dictionaries cannot be compared with `<`, so two tasks with the same priority would crash `heappush` if the tuple went straight from priority to task. The counter in the middle breaks ties in insertion order, so equal priorities come out first in, first out. The `queue.PriorityQueue` class wraps the same idea with locking for threads.
@mistakes
- **Assuming a BST is always O(log n).** Sorted input makes a chain; use a balanced structure or shuffle.
- **Recursion on deep trees.** A degenerate tree of 10,000 nodes overflows Python's recursion limit; walk it with a loop and an explicit stack.
- **Putting uncomparable items in a heap.** Add a counter as a tie-breaker between the priority and the item.
- **Sorting to get the top 3 of a million items.** `heapq.nlargest(3, data)` does it in one pass.
@keys
- A BST keeps smaller values left and larger right; lookups cost O(height).
- Balanced trees have height about log2(n); sorted inserts ruin an unbalanced one.
- In-order traversal gives sorted output.
- `heapq` is Python's priority queue: O(log n) push and pop, O(1) peek.

=== A14.3
@idea
CPython has a **global interpreter lock (GIL)**: only one thread at a time runs Python bytecode in a process. Threads still help when the program is **waiting**, because a thread releases the GIL while it sleeps, reads a socket or waits for a disk, so many downloads or database queries overlap nicely. They do not help when the program is **computing** in pure Python, because the threads take turns on one core. (Python 3.13 added an optional free-threaded build without the GIL; it is still experimental, and most code you meet runs with the GIL.)

To compute on several cores, use **processes**. The `multiprocessing` module and the friendlier `concurrent.futures.ProcessPoolExecutor` start separate Python interpreters, each with its own GIL, and send them work. The price is communication: arguments and results are **pickled** and copied between processes, so each task should do much more work than it takes to send, which means a few big chunks rather than one tiny task per item. Functions sent to a pool must be importable (defined at module level, not lambdas), and the code that starts the pool must sit under `if __name__ == "__main__":`, because on Windows and macOS each worker imports your main module.

A quick guide: waiting on many slow things, use `asyncio` (thousands of connections in one thread) or a `ThreadPoolExecutor` (simple, works with blocking libraries such as requests); heavy pure-Python computing, use a `ProcessPoolExecutor`; heavy numeric work, use NumPy or similar libraries, which do the work in C and release the GIL themselves. The `executor.map` interface is the same for threads and processes, so passing the executor in as a parameter lets you switch, and lets tests pass a stand-in.
@how
- Waiting (network, disk): threads or asyncio. Computing in Python: processes.
- `with ProcessPoolExecutor() as pool: results = list(pool.map(fn, chunks))`, under `if __name__ == "__main__":`.
- Send few, large chunks: pickling every argument and result costs time; `map(..., chunksize=...)` helps.
- Pool functions must be defined at module level (no lambdas or nested functions).
- Accept the executor as a parameter so code can switch between threads, processes and a test stand-in.
@example python norun: A CPU-bound job on four processes
import time
from concurrent.futures import ProcessPoolExecutor

def count_primes(bounds):
    lo, hi = bounds
    return sum(all(n % d for d in range(2, int(n ** 0.5) + 1)) for n in range(max(lo, 2), hi))

if __name__ == "__main__":
    ranges = [(i, i + 250_000) for i in range(0, 1_000_000, 250_000)]
    start = time.perf_counter()
    serial = sum(map(count_primes, ranges))
    t1 = time.perf_counter() - start
    start = time.perf_counter()
    with ProcessPoolExecutor(max_workers=4) as pool:
        parallel = sum(pool.map(count_primes, ranges))
    t2 = time.perf_counter() - start
    print(f"{serial} primes in {t1:.1f} s on one core, {parallel} in {t2:.1f} s on four (x{t1 / t2:.1f})")
@output
78498 primes in 4.8 s on one core, 78498 in 1.4 s on four (x3.4)
@note
Four chunks, one per worker, keep the pickling cost tiny compared with the work, so the speed-up is close to the number of cores (never quite equal: starting processes and the uneven chunks cost something). The browser runs Python in a single thread, so try this on your computer; your timings will differ.
@example python: Choosing a pool with a stand-in for tests
class InlinePool:
    """Runs jobs one by one in this process, with the same map interface as real pools."""
    def __init__(self):
        self.jobs = 0
    def map(self, fn, iterable):
        results = []
        for item in iterable:
            self.jobs += 1
            results.append(fn(item))
        return results

def word_counts(texts, pool):
    return sum(pool.map(lambda t: len(t.split()), texts))

pool = InlinePool()
print(word_counts(["the quick brown fox", "jumps over", "the lazy dog"], pool), "words in", pool.jobs, "jobs")
@note
Because `word_counts` only relies on `pool.map`, it runs with a `ThreadPoolExecutor`, a `ProcessPoolExecutor` or this stand-in, which makes tests fast and deterministic. (A real process pool could not pickle the lambda; with processes, pass a module-level function instead.)
@mistakes
- **Threads for CPU-bound Python.** The GIL makes them take turns; use processes.
- **One tiny task per item in a process pool.** Pickling dominates and the pool is slower than a loop; send chunks.
- **Starting a pool without the `__main__` guard.** Workers re-import the module and try to start pools of their own.
- **Lambdas in a process pool.** They cannot be pickled; define the function at module level.
@keys
- The GIL lets one thread run Python bytecode at a time.
- Threads and asyncio help with waiting; processes help with computing.
- Process pools pickle data, so send few, large chunks.
- Pass the executor in to switch implementations and to test.

=== A14.4
@idea
Every Python team uses some combination of the same building blocks: an **interpreter** (installed by the system, python.org, `pyenv`, `uv` or conda), a **virtual environment** per project so dependencies do not collide, an **installer** that downloads packages from PyPI, and a record of what the project needs. The tools differ mostly in how many of these jobs they combine. `pip` installs into whatever environment is active and `venv` creates environments; together with a `requirements.txt` they are the baseline every other tool is compared with.

**pyproject.toml** is the standard project file. Its `[project]` table (PEP 621) holds the name, version, supported Python versions and dependency ranges such as `requests>=2.31`; `[build-system]` names the backend (hatchling, setuptools, flit, pdm-backend, poetry-core) that builds the wheel. A **lock file** records the exact version of every package, including indirect ones, so every machine and CI run installs the same thing. **uv** (fast, written in Rust) combines pip, venv, pyenv and a lock file (`uv.lock`) in one tool; **Poetry** and **PDM** also manage the environment and lock (`poetry.lock`, `pdm.lock`); **Pipenv** uses its own Pipfile and Pipfile.lock; **conda** manages non-Python libraries too (compilers, CUDA, GDAL), which is why data science teams use it.

You do not need to master them all, but on a new team you should be able to recognise the files and run the project: `uv.lock` means `uv sync`, `poetry.lock` means `poetry install`, `Pipfile` means `pipenv install`, `environment.yml` means `conda env create`, and a plain `requirements.txt` means `python -m venv .venv` then `pip install -r requirements.txt`. Dependency names are compared after **normalisation** (PEP 503: lower case, runs of `-`, `_` and `.` become `-`), so `Django_REST.framework` and `django-rest-framework` are the same project.
@how
- Look for the lock file to know the tool: uv.lock, poetry.lock, pdm.lock, Pipfile.lock, environment.yml, requirements.txt.
- Declare dependencies as ranges in pyproject.toml; let the lock file pin exact versions.
- One virtual environment per project; never install project packages into the system Python.
- Commit the lock file for applications; libraries publish ranges and are tested against the latest versions.
- `uv python install 3.12` or `pyenv install 3.12` to get a specific interpreter.
@example python: Normalising and comparing dependency names
import re

def normalize(name):
    return re.sub(r"[-_.]+", "-", name).lower()

declared = ["Django_REST.framework>=3.15", "PyYAML", "typing_extensions; python_version<'3.11'"]
locked = {"django-rest-framework": "3.15.2", "pyyaml": "6.0.2", "typing-extensions": "4.12.2", "sqlparse": "0.5.1"}

names = [normalize(re.match(r"[A-Za-z0-9._-]+", d).group()) for d in declared]
for n in names:
    print(f"{n:24} locked at {locked.get(n, 'MISSING')}")
print("only in the lock file (indirect):", sorted(set(locked) - set(names)))
@note
The declared names are written three different ways, but after normalisation they match the lock file exactly. The package left over, sqlparse, is an indirect dependency pulled in by something else, which is precisely what a lock file is for: pinning the packages you never asked for by name.
@example bash: The same project with uv and with pip

# on a fresh clone:

@output

Resolved 6 packages in 180ms
Installed 5 packages in 9ms

@note
uv writes pyproject.toml (ranges), uv.lock (exact versions with hashes) and .python-version, and `uv run` makes sure the environment matches before running. The pip version works everywhere but mixes development and runtime packages in one frozen list; teams often split it into requirements.txt and requirements-dev.txt, or move to a tool with a lock file.
@mistakes
- **Installing into the system Python.** Packages collide between projects; always use a virtual environment.
- **Committing `.venv/` instead of the lock file.** Environments are machine-specific; the lock file is what reproduces them.
- **Pinning exact versions in a library's pyproject.toml.** It makes your library impossible to install next to others; use ranges.
- **Comparing package names as plain strings.** Normalise them first (PEP 503).
@keys
- pyproject.toml declares the project; a lock file pins every exact version.
- uv, Poetry, PDM and Pipenv combine environments, installing and locking; conda also handles non-Python libraries.
- Recognise the files and you can run any project on day one.
- Normalise package names before comparing them.

=== A14.5
@idea
Code is read far more often than it is written, and much of that reading happens through tools. **Docstrings** are the documentation those tools read: `help()`, editors' hover pop-ups, and documentation generators. Pick one style and use it everywhere; the **Google style** (`Args:`, `Returns:`, `Raises:` sections) and the **NumPy style** are both understood by **Sphinx** (through its napoleon extension) and by **MkDocs** with mkdocstrings, which turn docstrings and Markdown pages into a searchable documentation site. **doctest** runs the `>>>` examples inside docstrings, so the examples cannot silently go out of date.

**Type checkers** read your type hints and find bugs without running the code: `mypy` (the original), `pyright` (Microsoft's, fast, and the engine behind VS Code's Pylance), and `pyre` (Meta's). They catch the classic errors, such as passing `None` where a value is required or misspelling an attribute, and they make refactoring safer. **Formatters** end style debates: `black` and `ruff format` (nearly identical output) are the common choices, `yapf` is configurable and older. **Linters** such as ruff flag likely bugs and unused code, and many teams run all of these as pre-commit hooks and in CI.

**tox** and **nox** run the same commands (tests, linting, type checks, docs builds) in fresh virtual environments, often against several Python versions, so "works on my machine" becomes "works on 3.11, 3.12 and 3.13". tox is configured in an ini or toml section, nox in a Python file (`noxfile.py`). In CI, a version matrix often does the same job, but tox or nox lets every developer run exactly what CI runs.
@how
- Every public function and class gets a docstring: one summary line, then Args, Returns and Raises.
- Put runnable `>>>` examples in docstrings and run them with `pytest --doctest-modules`.
- Run a type checker in CI: `mypy src` or `pyright`; start lenient and tighten over time.
- Format with `ruff format` or `black`, lint with `ruff check`, and run them as pre-commit hooks.
- Use tox or nox to run tests, lint and type checks in clean environments on each supported Python version.
@example python: Reading docstrings like a documentation tool
import inspect

def overtime_pay(hours, rate, *, threshold=40, multiplier=1.5):
    """Pay for a week, with overtime above a threshold.

    Args:
        hours: hours worked in the week.
        rate: pay per normal hour, in cents.
        threshold: hours paid at the normal rate.
        multiplier: factor for hours above the threshold.

    Returns:
        Total pay in cents.
    """
    extra = max(0, hours - threshold)
    return round((hours - extra) * rate + extra * rate * multiplier)

doc = inspect.getdoc(overtime_pay)
print(doc.splitlines()[0])
print("signature:", inspect.signature(overtime_pay))
for name in inspect.signature(overtime_pay).parameters:
    print(f"  {name:10} documented: {name + ':' in doc}")
print(overtime_pay(45, 2000))
@note
`inspect` is what Sphinx, mkdocstrings and `help()` use: the summary line becomes the one-line description in tables of contents, and the signature and Args section become the parameter list. A checker can compare the two and flag parameters nobody documented, which is the exercise in this lesson.

@note
`nox` alone runs every session; `nox -s lint` runs one. Each session gets a fresh virtual environment, so missing dependencies in pyproject.toml show up here instead of on a colleague's machine. A tox.ini with the same environments does the same job with configuration instead of code.
@mistakes
- **Docstrings that repeat the function name.** Say what it does, what each argument means (with units) and what it returns or raises.
- **Examples in docs that are never run.** They rot; make them doctests.
- **Adding a type checker at full strictness to an old codebase.** Thousands of errors get ignored; start lenient and tighten module by module.
- **Arguing about formatting in code review.** Let a formatter decide and enforce it in CI.
@keys
- Docstrings are read by help(), editors, Sphinx and MkDocs; pick one style.
- doctest keeps examples honest.
- mypy, pyright and pyre find type errors without running code.
- black or ruff format for formatting; tox or nox to run checks on several Python versions.

=== A14.6
@idea
Python's web frameworks sit on one of two server interfaces. **WSGI** is synchronous: the server calls your application once per request and a worker (a thread or process) is busy until it returns. **Django**, **Flask** and **Pyramid** are WSGI frameworks (Django can also run on ASGI). **ASGI** is the async version: one event loop handles many requests and can keep connections open, such as WebSockets and server-sent events. **FastAPI** (built on Starlette), **Sanic**, **aiohttp** and **Tornado** are async frameworks. **gevent** takes another route: it patches the standard library so blocking code cooperatively switches between lightweight "greenlets", giving async-style concurrency to synchronous code.

The main design choice is **batteries included** versus **micro-framework**. Django ships an ORM with migrations, an admin interface, authentication, forms, templates and security defaults, so a database-backed site with logins needs very little extra code, at the price of doing things Django's way. Flask and FastAPI give you routing and requests and let you choose the database layer and everything else; FastAPI adds validation and OpenAPI documentation from type hints. Pyramid scales from small to large apps with explicit configuration; Tornado and aiohttp are lower-level async toolkits used for long-lived connections.

Every framework starts by **routing** a URL to a function. Django's `path("articles/<int:year>/", views.year_archive)` uses **converters** (`str`, `int`, `slug`, `uuid`, `path`) that both restrict what matches and convert the captured text, so the view receives `year` as an `int`. Routes are tried in order and the first match wins, so specific routes go before general ones. Under the hood each route compiles to a regular expression with named groups, which you build yourself in this lesson's exercise.
@how
- WSGI (Django, Flask, Pyramid) for classic request and response apps; ASGI (FastAPI, Starlette, Sanic, aiohttp) for async I/O and WebSockets.
- Django when you want an ORM, admin and authentication built in; Flask or FastAPI when you want to choose the pieces.
- Deploy WSGI apps behind Gunicorn or uWSGI, ASGI apps behind Uvicorn or Hypercorn.
- Order routes from specific to general; use typed converters so views get the right types.
- Never block the event loop in an async framework: use async libraries or run blocking calls in a thread.
@example python: Routing with typed converters, the Django way
import re

routes = [
    ("shifts/", "shift_list"),
    ("shifts/<int:pk>/", "shift_detail"),
    ("staff/<slug:handle>/shifts/", "staff_shifts"),
]
CONV = {"int": (r"\d+", int), "slug": (r"[-\w]+", str), "str": (r"[^/]+", str)}

def compile_route(route):
    pattern, types = "", {}
    for literal, conv, name in re.findall(r"([^<]*)(?:<(?:(\w+):)?(\w+)>)?", route):
        pattern += re.escape(literal)
        if name:
            regex, cast = CONV[conv or "str"]
            pattern += f"(?P<{name}>{regex})"
            types[name] = cast
    return re.compile(pattern + r"\Z"), types

compiled = [(compile_route(r), view) for r, view in routes]
for path in ["shifts/", "shifts/42/", "staff/ada-l/shifts/", "shifts/abc/"]:
    for (regex, types), view in compiled:
        m = regex.match(path)
        if m:
            print(f"{path:22} -> {view}({', '.join(f'{k}={types[k](v)!r}' for k, v in m.groupdict().items())})")
            break
    else:
        print(f"{path:22} -> 404")
@note
`shifts/42/` reaches the detail view with `pk=42` as an int, while `shifts/abc/` matches nothing and becomes a 404, because the int converter only accepts digits. The `\Z` anchor makes the whole path match. Django's real dispatcher adds includes, namespaces and reverse lookups (building URLs from view names) on top of this.
@example python norun: The same endpoint in Django, Flask and FastAPI
# Django: urls.py + views.py
from django.http import JsonResponse
from django.urls import path

def shift_detail(request, pk):
    return JsonResponse({"id": pk})

urlpatterns = [path("shifts/<int:pk>/", shift_detail)]

# Flask
from flask import Flask

@app.get("/shifts/<int:pk>")

    return {"id": pk}

# FastAPI

@api.get("/shifts/{pk}")

    return {"id": pk}
@output
GET /shifts/42/  -> {"id": 42}    (Django)
GET /shifts/42   -> {"id": 42}    (Flask)
GET /shifts/42   -> {"id": 42}    (FastAPI, plus a 422 error with details for /shifts/abc and docs at /docs)
@note
The routing idea is identical; the differences are in what surrounds it. Django keeps routes in a separate urls.py and gives you the ORM and admin, Flask uses decorators and stays small, and FastAPI reads the `pk: int` type hint to validate the request and generate interactive documentation.
@mistakes
- **Blocking calls inside async views.** One `requests.get` or `time.sleep` stalls every connection on the event loop; use an async client or run it in a thread.
- **General routes before specific ones.** `<slug:x>/` listed first swallows paths meant for later routes.
- **Rebuilding Django's admin and auth in a micro-framework.** If the project needs them, Django is often the faster start.
- **Picking a framework by benchmarks alone.** Team knowledge, ecosystem and built-in features usually matter more.
@keys
- WSGI is synchronous (Django, Flask, Pyramid); ASGI is async (FastAPI, Starlette, Sanic, aiohttp).
- Django is batteries included; Flask and FastAPI let you choose the parts.
- URL converters restrict and convert path parts; first match wins.
- gevent makes blocking code cooperative; async frameworks must never block the loop.

=== A14.7
@idea
Python releases a new version every October, and most changes are small conveniences you pick up as you go. A few change how code is written, and interviewers and code reviewers notice when you use them well. The course editor runs **Python 3.14**, so everything here works in the page.

**Python 3.12** cleaned up generics and typing syntax: `type Pair[T] = tuple[T, T]` declares a type alias, and `def first[T](items: list[T]) -> T:` declares a generic function without `TypeVar`. f-strings got a proper grammar (quotes and backslashes inside the braces now work), `itertools.batched(data, 3)` splits an iterable into tuples of three, and `@typing.override` marks a method that must override a parent's. **Python 3.13** brought a new interactive shell with colours and multi-line editing, even friendlier error messages, `copy.replace(obj, field=value)` for changing a field of a frozen dataclass or named tuple, `@warnings.deprecated` to warn callers at run time and in type checkers, `typing.TypeIs` for precise type narrowing, and an experimental **free-threaded build** without the GIL.

**Python 3.14** adds **template strings** (PEP 750): `t"Hello {name}"` looks like an f-string but evaluates to a `Template` object that keeps the literal text and the values separate, so a function can escape HTML, parameterise SQL or structure log messages safely. **Annotations are evaluated lazily** (PEP 649 and 749): a type hint can name a class defined later in the file without quotes, and the new `annotationlib` module reads them as values or as strings. `except ValueError, TypeError:` no longer needs brackets (PEP 758), `uuid.uuid7()` makes time-ordered IDs that sort well in databases, `pathlib.Path` gained `copy()` and `move()`, `compression.zstd` adds Zstandard compression, and the free-threaded build is now officially supported.
@how
- New code: `type` aliases and `def f[T](...)` generics (3.12+); `TypeVar` only when you must support older versions.
- Use `itertools.batched` for chunks, `copy.replace` for modified copies of frozen dataclasses.
- Use t-strings wherever a value is inserted into another language: HTML, SQL, shell commands, log messages.
- Forward references in annotations need no quotes in 3.14; use `annotationlib.get_annotations` to read them.
- Check `sys.version_info` or `requires-python` before using new syntax in a library others install.
@example python: Small 3.12 to 3.14 conveniences in one place
import copy, itertools, sys
from dataclasses import dataclass

@dataclass(frozen=True)
class Shift:
    who: str
    hours: int

s = Shift("Ada", 6)
longer = copy.replace(s, hours=8)               # 3.13: works on frozen dataclasses
print(s, "->", longer)

type Pair[T] = tuple[T, T]                       # 3.12: type statement with a generic
def swap[T](p: Pair[T]) -> Pair[T]:
    return (p[1], p[0])
print(swap(("in", "out")))

print(list(itertools.batched(["mon", "tue", "wed", "thu", "fri"], 2)))   # 3.12

for raw in ["8", "eight", None]:
    try:
        print(int(raw) * 2)
    except ValueError, TypeError:                # 3.14: no brackets needed
        print(f"could not double {raw!r}")
print("running on Python", f"{sys.version_info.major}.{sys.version_info.minor}")
@note
Each line replaces an older, wordier pattern: `dataclasses.replace` or a manual copy, `TypeVar("T")` declarations, a slicing loop for chunks, and `except (ValueError, TypeError):`. None of them is required, but they make intent clearer, and recognising them helps when you read newer code.
@example python: Lazy annotations and annotationlib
import annotationlib

class Team:
    def lead(self) -> Person:          # Person is defined below: no quotes needed in 3.14
        return self.members[0]

class Person:
    name: str
    team: Team | None = None

print(annotationlib.get_annotations(Team.lead))
print(annotationlib.get_annotations(Team.lead, format=annotationlib.Format.STRING))
print(Person.__annotations__)

def broken(x: NoSuchType) -> int:      # fine until someone asks for the values
    return 1
fr = annotationlib.get_annotations(broken, format=annotationlib.Format.FORWARDREF)
print(type(fr["x"]).__name__, fr["x"].__forward_arg__, fr["return"])
@note
Annotations are now computed only when something asks for them, so a class can refer to another defined later without writing `"Person"` in quotes, and importing a module no longer pays for evaluating every hint. Tools choose a format: VALUE evaluates the hints, STRING gives the source text, and FORWARDREF fills in placeholders for names that do not exist yet instead of raising NameError.
@mistakes
- **Building HTML or SQL with f-strings.** The value is glued into the text and injection becomes possible; use t-strings, a template engine or query parameters.
- **Using new syntax in a library that supports older Pythons.** Users on 3.12 get a SyntaxError on import; respect `requires-python`.
- **Assuming free-threading speeds up everything.** It needs a special build, and extensions must support it; processes remain the safe default for CPU-bound work.
- **`except ValueError, TypeError as e:`.** With `as`, brackets are still required: `except (ValueError, TypeError) as e:`.
@keys
- 3.12: `type` aliases, `def f[T]` generics, `itertools.batched`, `@override`.
- 3.13: new REPL, `copy.replace`, `@deprecated`, `TypeIs`, experimental free-threading.
- 3.14: t-strings, lazy annotations and annotationlib, `except A, B:`, `uuid7`, `Path.copy`.
- t-strings keep text and values apart so values can be escaped or parameterised.
